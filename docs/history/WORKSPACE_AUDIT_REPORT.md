## 1. Scope, methodology & verification provenance

### 1.1 What the project is

NightSeam Web is a static, no-bundler, no-backend deep-sky observation planner website:

- `landing/` — six public pages (index, features, about, download, privacy, impressum), **zero JavaScript**, generated release ledger.
- `web/` — the browser planner: `app.js` orchestrator (4,323 lines), `horizon.js` panorama editor (2,015 lines), `webstore.js` IndexedDB persistence/backup, thin re-export modules (`astro.js`, `nightrank.js`, `format.js`), `viztheme.js`, `imagecredits.js`, a generated `core.js` stub, `catalog.json` (12,176 objects, ~5 MB) and `catalog-provenance.json` (~6.74 MB sidecar).
- `core/` — the single astronomy/planning implementation (11 JS modules): Sun/Moon positions, precession, refraction, twilight windows, world-azimuth horizon bins, scoring. Baked by `scripts/build_core.py` into content-hashed trees `web/core/<hash>/` with current + N-1 retention.
- `catalog_data/` — website catalog source data, parsers, popularity policy, provenance sidecar generator.
- `scripts/` — build/check/release/deploy tooling (token graph, bake, staging, content-addressed immutable FTPS publication).
- `tests/` — 43 pytest files (288 top-level defs), 19 Node harnesses (tests/js/), 81 registered Playwright browser checks (tests/browser/, run outside pytest via `scripts/check_browser.py --web`).

Project authority documents: AGENTS.md (commands, invariants, token register), DESIGN.md (Workbench theme contract), BUGS.md (finding register), DEVELOPMENT.md (contracts), DECISIONS.md (rationale), RELEASES.md (validation receipts), IMPLEMENTATION_PLAN.md / REVIEW_REMAINING_IMPLEMENTATION_PLAN.md (status authority), HOSTING_CONFIGURATION.md, ENVIRONMENT.md, FUTURE_FEATURE_SCOPE.md.

Release state at audit time: public series v0.1.0–v0.1.1 (tags exist, v0.1.1 deployed per RELEASES.md). The 38 findings of an October 9 review (REV-001…038) are recorded as fixed **locally and unreleased** in phases 1–7. Open items per BUGS.md: A11Y-001 (human assistive-technology acceptance), HOST-DELIVERY-001 (live gzip), BROWSER-LOCAL-001 (monitoring-only).

## 2. A. Executive summary

**Overall assessment: this is an exceptionally disciplined codebase — in the top tier of projects observed in comparable audits.** The claims in AGENTS.md, BUGS.md and RELEASES.md are unusually truthful and verifiable. During this audit the auditor reproduced the recorded test counts (346 pytest passed / 1 optional skip), confirmed every cache-token register row against actual entry-point references, confirmed core bake integrity (current hash `8e090bcf870e108d` + N-1 retention; stub/manifest pairing exact; the N-1 tree differs from current in exactly the two files that explain token 47), confirmed the 12,176-object catalog count, the popularity-not-visible rule, elevation-never-reaches-astronomy-math, and the selection single-writer contract. No TODO/FIXME markers exist in tracked `.py`/`.js` source (grep verified). The astronomy/timezone/scoring math contains **no confirmed runtime bug**; the reference-anchor/mutation-test discipline genuinely proves its bite, and the known-wrong frozen lunar golden is asserted to *disagree* rather than silently pass ([digest, spot-checked]; see tests/test_core_fixtures.py:130-142 per digest).

**Most significant findings:**

1. **The full browser gate does not pass in this environment: `web-advanced-live-mode-and-responsive-warming` failed 3/3 runs**, including a quiet, isolated re-run ("cached scrubbing stays responsive", <2 s for three cached Catalog scrubs under 4× CPU throttling). RELEASES.md records 80/80 for the same commit the same day — so this is a timing-margin/environment problem, but it is reproducible here, and its mechanism is a real, independently confirmed performance issue (Catalog re-renders the entire view on every scrub tick, without the debounce Tonight has). **(F-01)**
2. **Public landing pages ship with no CSP, no Referrer-Policy, no nosniff at any layer**, while HOSTING_CONFIGURATION.md:58 implies such headers exist to preserve — a security-header asymmetry between the two served trees. Impact bounded today (landing has zero JS, no forms). **(F-02)**
3. **The catalog provenance sidecar is a pre-split artifact**: it records `app/data/supplement.csv` with a SHA-256 that does not match the shipped `catalog_data/data/supplement.csv`; the guard never validates input digests; regeneration would silently rewrite committed provenance bytes. **(F-03)**
4. **Build tooling has two "silent regression" holes** (corrupt core-manifest swallow → N-1 prune + token reset; non-atomic writes of `catalog.json`/`version.json`/core manifest), and the test suite has a **wiring gap that could silently drop 8 of 11 browser suites** with a green pytest. **(F-04, F-11, F-05)**

General codebase health: high maintainability, strong modular separation, pervasive race/generation guards, exemplary backup/rollback engineering. Weaknesses concentrate in: timing-sensitive performance margins, security-header asymmetry, provenance/manifest atomicity, guard-coverage blind spots, and accumulated stale documentation text.

**Major risks requiring attention:** the thin scrub-performance margin behind the failing gate; the silent-regression paths in build tooling; landing security headers; the provenance audit trail.

### 3.3 Major execution flows

- **Boot:** storage probe → catalog fetch (`catalog.json?v=10`, manifest-verified) → view render; global error/unhandledrejection banners (app.js:3911-3912); bootFailure splash path (app.js:947-962). Post-catalog awaits are uncaught (F-19).
- **Scoring flow:** night window anchored at site noon (core planning) → 6-min grid → shared nightStats/batch → obsCache shared by Tonight and Catalog → scores/rankings; panorama revision fingerprint prefix-invalidates per-grid caches (app.js:353-356).
- **Backup flow:** export (collectBackup, photos embedded truthfully) → import (200 MB cap, Hor.normalizePanos before restore, WS.stageBackup validates whole bundle, count confirmation, snapshot, applyWebSnapshot, records-committed flag gates rollback, double-failure surfaces safety-storage message) — matches AGENTS.md:29-31 precisely [digest, with direct verification of the rollback/selection code in the app.js:3551-3634 area].
- **Publication flow:** prepare_publication (local combined candidate, SHA-256 manifest, never connects) → make_release (bakes version.json, runs check_js + check_release --no-stage, stages, re-verifies) → ftps_deploy publish (validates entire bundle before connecting; immutable content-addressed graphs upload→verify→atomic rename; public HTML switches last, index.html last; refuses raw mutable website uploads; retains old release graphs).

### 3.4 Architectural strengths and weaknesses

**Strengths:** single-authority core with content-hash baking and N-1 retention; generation/epoch guards on every async path (tonightToken, detailGeneration, catalogPageGeneration, obsEpoch, `_wxGen`/`_wxContext` — all verified present [digest + direct reads at app.js:700-735]); baseline-based token guard closed against historic bypass classes; fail-loud infrastructure contract (exit 2 = infrastructure, exit 1 = failed check); truthful version stamping refusing guessed clean releases (build_web.py:57-62).

**Weaknesses:** app.js is a 4,323-line single orchestrator with inline view templates (coherent but monolithic); the baked-copy mechanism is dead-by-design at runtime if the hash directory 404s (mitigated only by N-1 retention); several guards rely on discovery heuristics with known blind spots (F-26); silent-regression holes in the build layer (F-04, F-11, F-13).

#### F-01 — Browser gate fails reproducibly: `web-advanced-live-mode-and-responsive-warming`
- **Severity:** High · **Category:** Testing / Performance · **Provenance:** [direct]
- **Location:** tests/browser/phase4_checks.py:226-268 (the check); web/app.js:4281-4285 (mechanism, per digest); web/app.js:4295-4298 (Tonight's debounce contrast, per digest).
- **Evidence:** Three runs, all failures: (1) full gate `python scripts/check_browser.py --web` → 79/80, output: `[FAIL] web web-advanced-live-mode-and-responsive-warming (11.3s) AssertionError: cached scrubbing stays responsive`, diagnostic line `active-horizon advanced mode, 4x CPU: first table 1.22s, complete 4.26s`; (2) full gate re-run → same failure (first table 1.28s, complete 4.38s); (3) isolated re-run on a quiet machine (all digest agents finished) `python scripts/check_browser.py --only advanced-live-mode` → 0/1, exit 1 (first table 1.13s, complete 3.83s). The first-table (<3 s) and complete (<8 s) bounds passed every time; the failing assertion is phase4_checks.py:267 `c.expect(scrubbed < 2, 'cached scrubbing stays responsive')` — the scrub timing print at :268 is never reached because the expect throws first (so the actual scrubbed value is unobserved). RELEASES.md:31-43 ("Commit validation — October 10, 2026") records "Full Chromium web gate: 80/80 passed" for this commit, and RELEASES.md:3-29 records another 80/80 run the same day. RELEASES.md:109-161 records an earlier "77/80 → fixed assertions → 80/80" narrative for phases 5-7.
- **Impact:** The release gate is environment-sensitive at exactly one assertion; on slower machines a fully green release claim is not reproducible. The scrub cost is dominated by the un-debounced full Catalog re-render per scrub tick (F-06), so the gate failure and the performance issue share a root cause.
- **Recommendation:** Add the same ~120 ms debounce Tonight uses to the Catalog scrub path (or throttle re-render to one animation frame), then re-baseline the timing bound with measured margins on the reference machine; document the gate's environment sensitivity in RELEASES.md if the bound stays as-is.
- **Confidence:** Confirmed (in this environment; passed in the maintainer's recorded runs on the same commit/date).

#### F-02 — Landing pages ship no CSP / Referrer-Policy / X-Content-Type-Options at any layer
- **Severity:** Medium · **Category:** Security · **Provenance:** [direct] (+ digest cross-confirmation)
- **Location:** landing/.htaccess:8-15 (only compression + cache rules) vs web/.htaccess:10-12 (sets CSP, Referrer-Policy, nosniff); no landing page has a meta CSP (all six heads checked; contrast web/index.html:23); HOSTING_CONFIGURATION.md:58.
- **Evidence:** The auditor read both .htaccess files in full and grepped all landing HTML for `Content-Security-Policy|http-equiv` — zero matches. HOSTING_CONFIGURATION.md:58-59 says "Preserve the CSP, Referrer-Policy and nosniff headers" while only the planner tree implements them. Impact bounded today: landing has zero `<script>` tags (grep verified) and no forms; `download.html` serves generator-produced HTML (escaped per build_changelog.py:251-259 [digest]). Caveat: .htaccess applies only under Apache; web/.htaccess:4-6 itself documents that Plesk/nginx may ignore it.
- **Impact:** Defense-in-depth gap and a doc-vs-config mismatch; nosniff/referrer are one-liners.
- **Recommendation:** Mirror the three header directives into landing/.htaccess (documenting the Apache-only caveat) or add a minimal meta CSP; align HOSTING_CONFIGURATION.md wording.
- **Confidence:** Confirmed (source level; live header behavior remains HOST-DELIVERY-001 territory).

#### F-03 — Provenance sidecar is a pre-split artifact; input digests stale and unguarded
- **Severity:** Medium · **Category:** Data integrity / Documentation · **Provenance:** [digest, spot-checked for guard behavior]; hash comparison performed by the digest agent via direct parsing
- **Location:** catalog_data/data/catalog_provenance.json:3 and :28; scripts/check_catalog_provenance.py:174; scripts/build_catalog_provenance.py:14-16, 105-111.
- **Evidence:** `:28` records `"path": "app/data/supplement.csv"` with sha256 `646e5ca9afc2…`; the shipped `catalog_data/data/supplement.csv` hashes to `73bff9a42bf7…` (computed by the digest agent with SHA-256, not by running project code). `:3` records a stale `"app/data/openned.csv"` path (its digest f892bf7d… DOES match current openned.csv — only the path label is stale). The 16 supplement designations show no drift vs the CSV (per-object alias/designation_history check [digest]). The guard (check_catalog_provenance.py:174) validates only `provenance["catalog"]["sha256"]` vs openned.csv — never the three input digests. NGC.csv/addendum.csv digests are unverifiable (those inputs are uncommitted by design). `web/catalog-provenance.json` is byte-identical to the source sidecar [digest], so the stale content ships to browsers.
- **Impact:** build_catalog_provenance.py:14-16 promises "SHA-256 digests make the exact input revision auditable and reproducible" — currently false for the supplement input; re-running the generator today would silently change committed provenance bytes (new path + new supplement digest), creating an unexplained future diff and a broken audit trail meanwhile. AGENTS.md's "source/provenance/display counts consistent" holds for counts; input-digest freshness is the gap.
- **Recommendation:** Regenerate the sidecar in a deliberate, documented commit; extend the guard to validate the three input digests where inputs are committed.
- **Confidence:** Confirmed.

#### F-04 — build_core.py silently swallows a corrupt manifest → token reset + N-1 prune; manifest written non-atomically
- **Severity:** Medium · **Category:** Architecture / Robustness · **Provenance:** [direct — auditor read scripts/build_core.py:126-175 in full and confirms the quoted code]
- **Location:** scripts/build_core.py:138-145 (swallow), :135-137 (defaults token=1, previous=None), :155-157 (prune via retention_keep), :166-171 (non-atomic manifest write).
- **Evidence (quote, verified):**
  ```python
  if MANIFEST.is_file():
      try:
          old = json.loads(MANIFEST.read_text(encoding="utf-8"))
          token = int(old.get("token", 1))
          old_hash = old.get("hash") or None
          previous = old.get("previous") or None
      except (OSError, ValueError):
          pass
  ```
  A crash mid-write (the manifest is written with plain `write_text`, no tmp+rename) or any corruption makes the NEXT bake: (a) reset token to 1 while all nine importers reference `./core.js?v=47` (cache-busting defeated; old baked dirs pruned so cached stubs 404); (b) lose the N-1 dir that cached older stubs need (build_core.py:72-82 documents why carrying previous matters). build_core exits 0. Downstream compensation exists (check_core.py:239-242 flags importers whose token differs from the manifest token) but only if a check runs after the silent reset.
- **Impact:** The "current + N-1 retention" invariant collapses silently exactly when protection is most needed.
- **Recommendation:** Fail loudly when a manifest exists but does not parse; write the manifest atomically (tmp + `os.replace`); prune only after the new tree and manifest are durable.
- **Confidence:** Confirmed (code); the trigger scenario (crash/corruption) has not been reproduced.

#### F-05 — Browser-gate wiring pin covers only 3 of 11 suites
- **Severity:** Medium · **Category:** Testing · **Provenance:** [digest for line numbers; check_browser.py imports read directly and confirm 11 module imports]
- **Location:** tests/test_browser_gate.py:18-40 (pins 21 check names; web_suite now registers 36), :44-46/:159-164/:167-178 (only phase4/landing/selection imports pinned); scripts/check_browser.py:19-29 (imports 11 suite modules — read directly, confirmed).

- **Impact:** Browser coverage can silently shrink without any test failing.
- **Recommendation:** Pin the full registered-check count/names against the runner's import list; derive both from one source.
- **Confidence:** Confirmed.

#### F-06 — Catalog re-renders the entire view on every scrub tick; per-render O(n) astronomy; re-sort per slider tick
- **Severity:** Medium (the direct, measured cost of F-01's failure) · **Category:** Performance · **Provenance:** [digest for line numbers; mechanism independently corroborated by F-01's measured failure]
- **Location:** web/app.js:4281-4285 (catalog scrub path renders without debounce; quoted by digest: `if (S.view === 'catalog') { if (ev.detail?.repaint !== false) renderCatalog(); return; }`), :4295-4298 (Tonight's deliberate 120 ms debounce with rationale comment), :1901-1905 (selectedVisibility → one E.altaz per object across activeCatalog() on every render when the visibility filter is active), :1816-1821 (computeCandidates re-sorts the 12k advanced pool per magnitude-slider input tick).
- **Evidence:** Topbar scrub in Catalog runs filter+sort over up to 12,176 rows and replaces the whole DOM (including the filter rail) per pointermove. Focus/caret restoration (app.js:1969-1979) prevents keyboard breakage but not the per-tick compute.
- **Impact:** Measurable jank cost in advanced mode; the measurable cost behind F-01.
- **Recommendation:** Debounce/rAF-coalesce Catalog scrub re-renders; memoize the sorted advanced pool and per-object selected-visibility per grid snapshot.
- **Confidence:** Confirmed (code paths); quantified impact environment-dependent.

#### F-07 — Horizon painting performs three O(n) passes per pointermove
- **Severity:** Medium · **Category:** Performance · **Provenance:** [digest]
- **Location:** web/horizon.js:1683-1706 (pointermove) → :1625-1630 (strokeAt) → :1543 (rebuildMaskNow re-rasterizes the mask from ALL strokes); :1272-1283 (overlay) → :1255-1270 (syncMaskCanvas rebuilds a full 720×360 ImageData, ~1 MB + 259,200-px loop, every call); :1504-1541 (renderStatus) → :1072 (dirty) → historyDirty → snapshot() deep-copies + JSON.stringify of ALL strokes (core panohistory.js:74-95, 160-162); updateProfileMetrics runs twice per overlay (:1470, :1540). Strokes bounded at 60,000 on restore (:277).
- **Impact:** At large stroke counts, every mousemove re-serializes/re-rasterizes everything — jank/frozen tab on low-end hardware. Typical sessions fine.
- **Recommendation:** Incremental mask/canvas updates; generation-counter dirty check instead of serialization; run metrics once per frame.
- **Confidence:** Likely (code path confirmed by digest; jank not demonstrated at typical sizes).
